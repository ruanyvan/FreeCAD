先回答你的三个问题

跟随一次导入，找到真正写入原生类型表的那条语句。
解释器在哪里建立？

主函数调用应用初始化，在配置初始化阶段进入 Py_InitializeFromConfig。场景零开始时，解释器已经存在。

模块怎样加载？

导入系统找到 Part.pyd，取得导出函数 PyInit_Part 的地址并调用。这个入口就是编译好的原生代码。

原生数据为何会改变？

模块入口调用 Part::Box::init()，最终由 Type::createType 直接修改当前进程的原生类型表。

这里没有两个进程之间的通信，也没有把脚本类型表自动翻译成原生类型表。主程序、解释器动态库、零件扩展库都在同一进程内；各层交接的是函数调用、对象指针、字符串和明确的所有权责任。

特别留意返回值：PP_Load_Module 返回模块对象指针；loadModule 成功返回真；Type::importModule 没有返回类型数据。真正让原生表改变的是导入过程中的初始化行为，不能在返回值里寻找一份“传回来的注册表”。

字符串类型名 → 模块名 → 扩展库入口 → 类型登记 → 工厂函数指针 → 原生对象

解释器运行库PyInterpreterState

组织模块、命名空间、执行状态和异常。

解释器不是一个后台控制台窗口。它是链接进当前进程的运行库与状态。原生程序可以进入它的接口执行代码，再同步返回，不必启动独立的脚本进程，也不必打开交互终端。

名称真实含义不要混淆
InterpreterSingleton工程的管理单例，构造时只把 _global 设为空管理对象构造不等于运行库初始化。
PyInterpreterState解释器上下文，模块与内置对象等状态归它管理导入一个模块不等于新建一个解释器。
PyThreadState关联解释器的线程执行状态_global 实际是这种指针，不是全局变量字典。
PyObject*脚本对象的统一接口指针不能把任意原生类指针强转成它。
PyTypeObject脚本类型对象，包含属性访问、调用、析构等函数槽与原生工厂的类型登记不同。
Base::Type工程类型编号的轻量封装编号索引到原生类型资料，不携带解释器。

嵌入解释器解决“主程序如何调用脚本”；扩展模块解决“脚本如何调用原生能力”。本工程同时使用两者，所以一次调用可以从原生程序进入导入系统，再回到原生模块入口。官方嵌入说明、接口总览。

管理对象的创建与解释器的创建是两件事

Base::Interpreter() 取得管理单例。真正的 init() 检查 Py_IsInitialized() 后，才决定是否初始化运行库。外部脚本进程已经建立运行库后再导入核心模块，会走复用已有解释器的分支；你的原生实验走的是自己建立解释器的路径。

初始化配置究竟控制什么

本版本先用隔离配置填入默认值，再显式把 isolated 改为零、用户安装目录开关设为一。不能只看函数名就说它完全隔离，也不能推断所有普通解释器默认值都恢复了。参数经配置接口传入，最终配置参与建立路径、标准模块与执行环境。PyConfig_Clear 释放配置资源，不会销毁解释器。

运行库内部由 Py_InitializeFromConfig 组织运行时、核心和主环境初始化。核心流程创建解释器状态和首个线程状态，建立解释器锁，初始化基础对象、内置模块和导入系统；主环境阶段继续完成标准流和主模块等环境。“创建解释器”具体就是分配并连接这些原生状态。初始化入口、解释器与首线程、配置接口。

为什么后面仍遇到初始化调用

初始化辅助函数末尾和 PP_Init 都会调用 Py_Initialize；已经初始化时这个兼容入口直接返回，不清空模块缓存，也不建立第二个解释器。要捕获首次创建，应在配置初始化处设断点。

初始化后，管理对象通过 PyEval_SaveThread 保存当前线程状态并释放解释器锁。之后包括主线程在内，操作脚本对象时都需要按工程约定重新持锁。

核心模块与扩展模块的两种入口

一个入口来自显式登记，另一个入口来自动态库导出符号。

PyImport_AppendInittab 登记“模块名 → 初始化函数指针”。它告诉导入系统以后怎样创建核心模块，尚未执行入口，更不是登记长方体。应用构造随后调用 setupPythonTypes，设置 ApplicationMethods 并导入核心模块，入口用 PyModule_Create 建立模块对象。

登记位置登记内容什么时候发挥作用
内置模块入口表FreeCAD → init_freecad_module解释器建立前登记，实际导入时调用。
模块方法表方法名称、回调地址、参数约定创建模块时成为脚本可调用对象。
原生类型表Part::Box → 编号 → &Part::Box::create零件模块初始化时登记，创建模型时使用。
脚本模块字典Part.Shape → 脚本类型对象发布给脚本属性查询。

核心模块入口名称可以不是 PyInit_FreeCAD，因为函数地址已经显式登记。磁盘上的 Part.pyd 则需要按约定查找 PyInit_Part；工程宏 PyMOD_INIT_FUNC(Part) 正是生成这个导出入口。语言链接与导出声明确保运行库能按名称找到它。

启动脚本会扫描模块目录、补充搜索路径并执行各目录的初始化脚本。扫描目录不代表已经导入每一个二进制扩展；本次场景零开始时，长方体仍未登记。

本实验链接了零件扩展库，系统可能在主函数运行前已映射该库。动态库映射、解释器调用模块入口、工程登记类型是三个不同动作。调试器模块列表出现零件库，不证明类型已经登记。

逐层拆解你的调用链

每一层完成不同职责，返回值也承担不同含义。
层主要动作结果
createInstanceByName允许加载时先导入，再查类型、调用工厂返回原生实例指针。
Type::importModule从类型名前缀取模块名，跳过核心模块及已记录模块成功后记录到 loadModuleSet。
loadModule取得解释器锁，调用导入工具成功返回真，失败抛原生异常。
PP_Load_Module区分主模块、虚拟模块、重载和普通导入普通成功路径返回借用模块指针。
PyImport_ImportModule标准导入，使用缓存或查找并初始化模块成功返回新引用；失败返回空并设置异常。

当前源码顺序是 loadModule=true 时先调用导入，再调用 fromName。集合让重复调用快速返回，但不能改述为“先查类型，缺失时才调用导入”。

导入工具默认 PP_RELOAD=0。主模块走 PyImport_AddModule，这个接口只取得或建立模块容器，不执行同名文件。普通零件模块走真正的导入接口；取得新引用后在工具内部减去一次，依赖模块缓存继续持有对象，再把借用指针返回。这个包装函数改变了标准接口的引用合同。

原实验注释还有一处简化：当前 Document::addObject 实际调用 getTypeIfDerivedFrom(..., true)，校验继承关系后调用 createInstance()，并未直接调用 createInstanceByName。两条路线共用导入与工厂机制。

类型登记：到底哪一行改了原生数据

注册的核心是名称、父类型、编号与创建函数地址。

模块入口先导入材质依赖，建立模块对象、异常及脚本类型，随后登记原生特征。原始体登记在长方体之前，满足父类型必须存在的条件。

长方体使用 PROPERTY_SOURCE(Part::Box, Part::Primitive)。它包含原生类型系统宏，还连接属性元数据。下列是教学展开，省略其他声明，不是要求添加的实现： 

// 工厂创建原生对象；登记时仅保存它的地址。
void* Part::Box::create()
{
    return new Part::Box();
}

// 宏为本类型生成的登记流程。
void Part::Box::init()
{
    // 1. 登记名称、继承关系与工厂。
    initSubclass(classTypeId, "Part::Box", "Part::Primitive", &Part::Box::create);
    // 2. 连接父类属性元数据。
    propertyData.parentPropertyData = Part::Primitive::getPropertyDataPtr();
}

initSubclass 核对尚未登记、查找父类型，再调用 Type::createType。后者用数组长度作为编号，把新 TypeData 放进 typedata，向 typemap 写入名称到编号的映射。返回的编号赋给类的静态类型成员。

位置示意内容作用
typemap"Part::Box" → k名称转索引。
typedata[k]名称、父类型、类型编号、instMethod=F提供继承判断与实例化入口。
classTypeId类型编号 k类和实例查询工程类型。
工厂地址 F&Part::Box::create被调用时才执行构造。

登记不等于创建模型。导入返回后，工厂入口查询这张表并调用函数指针，才进入长方体构造函数。场景零的临时对象没有加入文档，随后被删除；场景一的对象交给文档管理。

这张表属于基础库，零件扩展通过链接的基础接口调用同一个登记函数。原生数据由原生代码直接修改，解释器只是触发了模块初始化。把基础实现错误地静态复制进多个扩展可能造成多份全局表，但那不是当前工程的正常架构。

      脚本对象怎样指向原生对象
      类型登记建立工厂；包装建立对实例的访问通道。
      

      脚本调用 doc.addObject("Part::Box", "Box") 时，文档包装的方法表把名称映射到生成的静态回调。回调校验包装有效性，进入手写的 DocumentPy::addObject，解析参数并调用原生文档方法。原生对象创建并归入文档后，包装层调用它的虚函数 getPyObject()。  
      

      具体包装类型很重要：长方体继承原始体的实现，调用 Part::Primitive::getPyObject()。首次创建 PrimitivePy(this)，缓存到 PythonObject；以后返回同一包装对象的新引用。本次 type(box) 是 PrimitivePy，box.TypeId 却是 Part::Box，说明包装类型与原生类型不是一一对应。
      

      脚本变量 box ──强引用──→ 包装对象 W：PrimitivePy
                              │ _pcTwinPointer
                              ▼
文档对象集合 ──管理──→ 原生对象 B：Part::Box
                              │ PythonObject（包装引用）
                              └───────────────────→ W

W 的脚本类型 → PrimitivePy::Type → 基类包装的属性槽与方法表
B 的工程类型 → Part::Box::classTypeId → 原生类型表
      

      这不是复制整个模型到脚本堆。包装保留原生指针，操作由绑定代码转发；但具体属性返回值可以是新对象，不能把所有返回值概括成共享引用。
      

      包装代码如何产生
      工程的包装描述文件、生成器和手写实现相互配合。生成文件提供类型槽、方法表、入口与异常边界；手写的 *PyImp.cpp 执行业务访问。当前生成结果在构建目录，源目录中没看到它，不代表这里使用了自动识别任意原生类的反射机制。
      

      原生虚函数表与脚本类型的函数槽也不同。调用 getPyObject() 使用原生虚分派；脚本访问属性则通过脚本类型槽进入包装。两者由显式生成和手写逻辑连接。

      属性槽收到的仍是 PyObject*。容器按名称找到属性，再虚分派到它的转换函数。长方体尺寸是长度属性，接受字符串、整数、浮点或量值包装，转成原生量值并处理约束与单位。实测 "2 cm" 写入后内部数值为 20 毫米。    
      

      真正写入是 _dValue = lValue，前后由属性通知包围。通知继续进入容器、文档事务和特征回调。解释器不会自己发现字段变化，也不会自动替原生字段建立撤销或依赖传播。
      

      读取属性不一定得到活引用
      PropertyQuantity::getPyObject 从当前数值与单位构造新的量值。因此 q = box.Length 后，把长方体长度设为 30，q.Value 仍是原来的 20。这已由本次探针验证。
      

      操作路线区别
      box.Length = 20包装 → 转换 → 原生写入脚本入口承担输入类型、单位和范围规则。
      box->Length.setValue(20)直接进入原生属性写入绕过脚本转换，仍执行属性前后通知。
      q = box.Length具体属性构造返回值长度返回独立量值，不是尺寸字段引用。

      12 / 22
      从对象布局到调用约定
      统一对象指针如何变成正确的原生函数调用。
      

      统一对象头解决“这是什么”
      

      常规运行库对象包含引用计数信息和类型指针。类型指针指向描述行为的脚本类型对象：怎样访问属性、能否调用、怎样释放。整数、字符串、模块和扩展包装都能通过统一指针交给接口，但具体数据布局不同，所以转换前需要类型判断或使用带错误检查的转换接口。
      

      一般扩展结构使用 PyObject_HEAD 引入对象头；本工程的包装基类则直接继承 PyObject，再由自己的构造和析构配合管理。通过 PyObject* 看它时操作的是脚本对象接口；通过合法的包装类型转换后，才访问 _pcTwinPointer 指向的模型。不要假定包装指针与模型指针数值相等，更不能从脚本 id(box) 推出原生长方体地址。
      

      方法表解决“调用哪个地址”
      

      文档包装方法表中，名称 addObject 对应生成的 staticCallback_addObject，同时标注位置参数与关键字参数约定。运行库按这个约定准备自身、参数元组与关键字字典，再进入静态入口。静态入口取得文档包装，调用手写成员实现。函数指针存在并不足以正确调用；参数约定必须一致。 
      

      脚本：doc.addObject("Part::Box", "Box")
  方法查找：名称 → 回调地址 + 参数约定
  self：文档的脚本包装指针
  args：("Part::Box", "Box") 这个参数元组
  kwd：关键字参数字典，或空指针
    ↓
  静态回调 → DocumentPy::addObject(args, kwd)
    ↓ 参数解析
  sType：指向类型名的字符串
  sName：指向对象名的字符串
    ↓
  getDocumentPtr()->addObject(sType, sName, ...)
      

      解析格式中的 s 表示字符串转换，| 表示后续可选参数，O 接收对象指针，O! 还要求指定类型。当前入口把类型名、可选名字、代理对象和布尔参数等逐项解析，解析失败返回空并保留异常。借用得到的字符串或对象不能脱离参数生命周期保存；需要长期保存时应复制原生字符串或明确持有脚本引用。
      

      数据转换是显式代码
      

      脚本数据常见原生接口注意的边界
      整数PyLong_AsLong原生整数范围可能更小，溢出是错误；当前长度转换代码也使用这个接口。
      浮点PyFloat_AsDouble转换结果与错误状态一起检查。
      字符串PyUnicode_AsUTF8返回的缓冲区依附对象，不是需要自行释放的新字符串。
      元组、字典参数接口或容器接口容器持有元素引用；取出、插入的引用责任依具体接口而定。
      模型包装类型校验 → 包装指针 → 原生指针先保证包装有效，再使用活模型。
      返回原生数值构造脚本数字或量值对象转换出的是返回对象，不是自动把原生栈变量暴露给脚本。
      

      模块也不是一个原生名字空间的自动镜像。它有脚本字典，字典保存名称到脚本对象的引用；方法表和类型登记代码主动把能力发布进去。只有被发布的成员可经脚本查到，任意原生静态变量不会自行出现在模块里。
      

      13 / 22
      引用计数：管理的是引用责任
      先说清谁负责释放，再看计数变化；不要靠一个数字猜所有权。
      

      新引用表示调用方取得一份强引用责任，最终必须释放或转交。借用引用表示没有得到这份责任，不能擅自减计数；想跨越所有者的生命周期保留它，就先取得自己的强引用。偷取引用表示接口接管调用方已有的那份责任。它们描述的是合同，不是指针是否指向新分配对象。
      

      接口或操作成功时的责任当前链条中的处理
      PyImport_ImportModule新引用普通导入工具内部释放一次。
      PP_Load_Module当前包装函数返回借用引用loadModule 不再减计数。
      PyImport_AddModule借用引用不会因获取主模块而新增释放责任。
      PyModule_GetDict借用引用字典由模块持有，使用时必须保证模块仍存在。
      PyDict_GetItemString借用引用读取缓存项不转移所有权。
      PyObject_GetAttrString新引用即使取到原有属性，也要释放这份引用。
      PyObject_CallObject成功返回新引用调用结果使用完需要释放。
      getPyObject()工程约定向调用方提供新引用可以是同一缓存包装对象增加引用，而非每次新建。
      PyModule_AddObject成功时偷取值的引用失败时不能按成功转交处理。
      PyTuple_SetItem偷取传入项的引用不要再按借用接口的方式释放该项。
      

      在零件普通导入里，标准接口返回 M 的新引用；模块缓存仍持有它；工具减去本次获得的引用，再把指针借给调用方。这样解释了为何减计数后还能返回指针，也说明这段写法依赖缓存持有条件，不能当成任意对象通用模板。 导入接口合同、模块接口合同。
      

      工程的自动管理包装
      本工程常见 Py::Object(ptr, true) 表示接管已有的新引用；从借用指针构造普通包装会按其接口建立自身引用。Py::new_reference_to 给返回者一份新引用。阅读时必须核对具体构造函数约定，不能凭布尔值名字猜。实际原始体包装创建后就由自动管理对象接管，再以新引用形式返回。
      

      把引用计数当成“变量个数”会误判：容器、缓存和临时对象也持有引用；3.12 还存在不会按普通方式增减的永久对象。Py_DECREF 可能触发对象析构和用户代码，因而也是一次可能重入的调用边界。引用计数规则。

      原生侧主动调用脚本：两条路线
      执行文本与调用对象共享同一解释器，但输入、命名空间和返回规则不同。
      

      路线一：编译并执行字符串
      runString 持锁取得主模块，借用模块字典，把它同时作为全局和局部命名空间传给 PyRun_String(..., Py_file_input, dict, dict)。这会把语句文本编译为代码对象并执行。顶层赋值写入该字典，函数定义产生函数对象，导入语句继续调用导入机制。
      

      普通语句执行的结果不是最后一行表达式的值。runString 返回的是执行结果的文本表示，通常为 "None"。要取表达式结果，应看 runStringObject 使用的 Py_eval_input，或者从明确的对象接口取值。文件输入、单个表达式与交互输入是不同编译模式，不能互换。
      

      路线二：构造参数并调用可调用对象
      当数据来自变量，应优先传对象，而不是拼接语句文本。下面是放在“应用初始化后、结束前”的局部教学片段，需要工程已有的解释器头文件和脚本包装类型。片段不改动现有实验，未作为新增原生目标编译。
      

      // 1. 先取得解释器锁；它必须比下方对象更晚析构。
Base::PyGILStateLocker lock;

// 2. 导入模块，并接管标准接口返回的新引用。
PyObject* rawModule = PyImport_ImportModule("math");
if (!rawModule) {
    throw Base::PyException();
}
Py::Object module(rawModule, true);

// 3. 取得函数和参数。局部包装在锁释放前结束。
PyObject* rawFunction = PyObject_GetAttrString(module.ptr(), "sqrt");
if (!rawFunction) {
    throw Base::PyException();
}
Py::Object function(rawFunction, true);
Py::TupleN arguments(Py::Float(144.0));

// 4. 调用并接管结果，再按明确类型转换。
PyObject* rawResult = PyObject_CallObject(function.ptr(), arguments.ptr());
if (!rawResult) {
    throw Base::PyException();
}
Py::Object result(rawResult, true);
double answer = PyFloat_AsDouble(result.ptr());
if (PyErr_Occurred()) {
    throw Base::PyException();
}
// answer 的期望值为 12.0；这里只保留原生数值。
      

      上面每个取得新引用的操作都立即交给自动管理对象，失败转换为原生异常。作用域退出时先销毁结果、参数、函数和模块包装，最后释放锁。若把脚本对象包装放到锁的外层，即使函数调用时持锁，析构时仍可能在无锁状态减引用。
      

      再深入一层：可调用对象可能是脚本函数，也可能是扩展函数。前者进入解释器帧与字节码求值，后者经调用约定直接进入原生函数地址。所以“调用脚本接口”不代表一定执行一段脚本字节码。扩展函数与调用约定。
      

      15 / 22
      异常如何穿过语言边界
      错误标志与返回值是一对合同，原生异常不能任意穿过运行库边界。
      

      多数返回对象的运行库接口失败时返回空，并在当前线程的解释器状态中保留异常。原生调用方需要同时理解这两个信号。不能把空指针当成普通空结果继续使用，也不能设置了异常后又返回一个成功对象。数值转换接口的错误值可能与正常值相同，必须按合同检查异常状态。
      

      方向实际处理本次源码依据
      导入失败 → 原生调用者导入接口返回空；loadModule 区分退出异常，其余转为 Base::PyException
      原生文档方法失败 → 脚本调用者生成回调捕获原生异常，设置脚本异常，再返回空
      原生属性转换失败 → 脚本赋值属性分派捕获异常，设置脚本异常，再返回错误状态
      脚本特征执行失败 → 原生重算执行桥读取解释器异常并转换，再由特征流程处理
      

      Base::PyException 读取并清理解释器中的异常信息，将类型、消息、回溯等用于原生处理。调试时，先查看运行库失败返回处的异常，再查看转换后的原生异常；转换完成后原始异常槽可能已经清空，不能据此认定从未出错。
      

      异常分类用异常类型或错误枚举，例如 PyErr_ExceptionMatches；错误消息供人阅读，不应用消息子串决定程序分支。底层调用已经设定明确异常时，清理自己的资源并传播即可，不要随意覆盖成无上下文的通用错误。解释器异常合同。
      

      16 / 22
      线程状态与解释器锁
      锁保护解释器访问；它不自动保护整个模型业务。
      

      初始化线程释放解释器锁后，loadModule、runString 等入口使用 PyGILStateLocker。构造调用 PyGILState_Ensure，析构调用 PyGILState_Release；局部对象既保证正常返回配对，也保证异常退出配对。它还能处理线程所需的运行库关联状态，不是单纯给一个整数加锁。
      

      进入零件入口时已持锁，入口再调用脚本导入材质模块，形成嵌套调用。工程使用的作用域锁记录进入前状态，因此嵌套结束不会把外层需要的锁无条件释放。代码在一次同步调用中多次穿过边界，不需要排队给另一个“解释器线程”。
      

      什么时候可以暂时释放
      PyGILStateRelease 在已持锁前提下保存线程状态并释放锁，析构时恢复。适用情况是耗时的纯原生计算，且这段区间不访问脚本对象、不改引用、不触发脚本回调。不能只看到几何计算就立即释放：若沿途可能经属性通知回调脚本，必须先审查整条路径。
      

      解释器锁并不保证文档、几何对象和界面线程安全。即使线程可以安全调用运行库，也仍要遵守工程的文档线程约定。常见死锁是主线程持解释器锁等待工作线程，而工作线程正在等待同一把锁进入脚本回调。
      

      本页讨论实际使用的常规 3.12 构建。不要把本工程的单例管理方式直接推广到多个子解释器，也不要把较新无全局锁构建的行为套过来。工程的进程级静态类型表、静态脚本类型和缓存引用需要专门设计，不能仅通过多建解释器就获得隔离。线程状态与解释器锁。
      

      17 / 22
      生命周期：有脚本引用不等于模型还活着
      脚本包装与原生业务对象的销毁由不同机制控制。
      

      文档管理长方体，脚本引用管理包装对象。关闭文档后，原生对象可以销毁，但脚本变量仍持有包装。原生文档对象析构因此主动调用 setInvalid()，清理跟踪属性并把原生指针置空。包装属性入口检查有效性后抛引用失效异常，阻止继续访问已经删除的模型。 
      

      本次实测：文档打开时两次取同名对象得到同一个包装；关闭文档后，旧变量访问长度抛出 ReferenceError。这比“脚本引用计数保证原生对象存在”更准确。几何值或独立量值等其他包装可能有不同所有权，必须逐类看实现，不能由文档对象推断所有包装都不拥有原生对象。
      

      退出次序也属于正确性
      原实验先关闭所有文档，再进入应用销毁。应用销毁流程清理应用状态与观察者，调用解释器结束，再销毁管理单例和原生类型表。解释器结束函数恢复保存的线程状态，进行模块清理并调用 Py_Finalize。 
      

      仍有后台线程调用解释器、静态包装在结束后才减引用、回调仍指向已销毁模型，都会让退出阶段成为错误发生点。不能把重复初始化/结束解释器当成扩展模块热重载；运行库与第三方扩展的进程级状态未必能完整重建。

      进阶：原生重算反过来执行脚本特征
      同一个模型调度可以跨边界回调，再把结果写回原生属性。
      

      普通长方体在原生 execute() 中建模；脚本特征则把实现对象保存在代理属性。重算进入 FeaturePythonT::execute，再调用 FeaturePythonImp::execute。后者持锁，通过已保存的可调用对象执行代理方法；常用分支把当前原生对象的包装作为参数传入。
      

      原生文档重算
  → 脚本特征的原生 execute
  → 代理执行桥取得解释器锁
  → 调用代理的 execute(obj)
  → 脚本调用 Part.makeBox(...)
  → 原生几何算法生成形状
  → 脚本执行 obj.Shape = ...
  → 属性包装转换
  → 原生形状属性写入与通知
  → 返回原生重算调度
      

      下列练习展示一次完整回路，在独立临时文档中执行。它与本页已验证的普通长方体探针不同，属于供你逐步调试的练习。代理只负责生成结果，不在属性变化回调里递归重算文档。
      

      import FreeCAD as App
import Part

# 代理只实现几何生成，文档继续持有模型对象。
class CubeLogic:
    def execute(self, obj):
        size = obj.Length.Value
        obj.Shape = Part.makeBox(size, size, size)

doc = App.newDocument("CallbackLesson")
obj = doc.addObject("Part::FeaturePython", "Cube")
obj.addProperty("App::PropertyLength", "Length")
obj.Length = 12
obj.Proxy = CubeLogic()
doc.recompute()
print(obj.Shape.Volume)       # 期望 1728
App.closeDocument(doc.Name)
      

      当前桥中，代理显式返回假表示没有处理，可继续走父类实现；普通无返回值的方法返回空值对象，按已处理计算。还有绑定代理对象的另一种调用约定，以及未实现异常的专门分支。学习时先掌握常用的传模型参数路线，再对照源码理解这些明确分支，不能把所有“返回空”当成执行失败。
      

      设计这类混合特征时，原生层继续拥有文档身份、属性和调度，脚本层实现可替换算法。数据通过明确参数与属性写回，不通过比较前后字段去猜变化来源。

      从入门到熟练：六组验证练习
      每个练习都先预测，再看断点与数据；不要只背最后输出。
      

      一 · 创建时机
      在配置初始化之前、应用初始化之后分别观察运行库状态。为什么导入工具中再次初始化不清空模块？
      核对解释
      首次配置初始化建立运行库；后续兼容初始化在已初始化状态直接返回。管理单例构造与运行库创建不同。
      

      二 · 注册与创建分离
      场景零分别停在长方体登记与构造位置。哪个时刻有工厂地址？哪个时刻才有实例？
      核对解释
      登记后表里已有创建函数指针，但尚无本次实例。回到工厂调用后才进入构造；场景零随后主动删除临时实例。
      

      三 · 再次导入
      重复同类型创建，观察工程已加载集合与模块缓存。模块入口是否再次执行？
      核对解释
      正常第二次调用被工程集合跳过；直接重复标准导入也通常命中模块缓存。这两层缓存不是一张表。不要删除缓存后推断能可靠重跑原生初始化。
      

      四 · 值与身份
      对比 doc.getObject("Box") is box 与“保存量值后改变长度”。为什么前者保持对象身份，后者不随模型变化？
      核对解释
      模型缓存包装对象并返回新引用；长度读取构造独立量值。相同的读取语法不代表相同的数据传递方式。
      

      五 · 转换与错误
      在临时文档把长度赋为 "2 s"，观察单位转换异常如何回到脚本；再比较原生负尺寸写入与脚本负尺寸写入。
      核对解释
      秒与长度单位不匹配，转换层抛异常，由生成入口转回脚本。当前长度脚本入口会约束负值，而原生浮点写入没有这一步；模型算法随后仍有自己的有效性检查。两种失败不能混同。
      

      六 · 活包装与已删除模型
      保留脚本变量，关闭文档后再访问。怎样证明错误来自原生生命周期结束，而非模块被卸载？
      核对解释
      在原生对象析构与包装失效处观察；包装仍被变量引用，模块也仍在缓存中，但原生指针已经清空，属性入口因此报引用失效。

      故障定位与工程边界
      按失败发生的层定位，避免把所有问题都归结为“解释器没加载”。
      现象先查哪一层应收集的证据
      初始化就失败运行库与标准库部署真实动态库、版本、位数、配置路径、标准库编码模块是否存在。
      找不到模块模块查找模块名、搜索路径、查找器结果、目标文件路径。
      模块文件存在但装载失败系统依赖依赖库是否可解析、二进制位数、解释器小版本、调试与发布运行库是否匹配。
      导入成功但类型仍不存在模块初始化与登记是否导入同名其他模块、实际文件来源、入口是否登记该类型、类型名是否正确。
      重复初始化断言缓存与重复登记是否手动调用入口、移除缓存、混用多个基础库实例。
      包装存在但属性访问失败原生生命周期文档是否关闭、包装是否失效、是否仍保存旧模型引用。
      修改数值但形状不符模型通知与重算输入是否转换成功、通知是否到达、对象与文档重算阶段、算法错误。
      偶发崩溃或退出卡死引用、锁与线程借用引用是否越界、析构是否持锁、是否重入、线程退出与解释器结束顺序。
      

      需要增加诊断时，一次覆盖完整边界：主进程与运行库版本、模块请求名与实际文件、入口开始与返回、注册名称与工厂地址、对象与包装地址、属性输入类型与转换值、异常类型、线程与生命周期事件。诊断使用事件发生时的真实数据，不靠事后对比猜来源。本次未修改业务代码加入日志。
      

      进一步掌握时要能解释的限制
      

      脚本类型登记通过 PyType_Ready 补全继承槽，再把类型发布到模块；原生登记则保存工厂和父类型。这两条路线可以发生在同一个模块入口，却不能合并成一个“注册动作”。
      

      单阶段扩展与静态类型容易依赖进程级状态。多个解释器、模块卸载、热更新和并行调用都需要重新审查所有权。公共稳定接口也不等于任意扩展能跨解释器小版本通用；使用完整类型布局的扩展必须匹配其编译与运行条件。
      

      绑定生成器和自动管理包装减少重复代码，但不能代替你决定模型归属、值拷贝语义、异常映射与线程合同。真正能独立排查混合编程问题，意味着你能指出每个边界传递的类型、持有者、引用责任，以及失败返回时留下的状态。
